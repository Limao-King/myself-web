# 童话冒险 DEMO

## 概况
故事方面，原型脱胎于我的剧本项目，但并非简单复用，而是基于原剧本中核心人物的弧光，在新的童话世界的世界观下进行贴合游戏的再塑造。讲述汉斯与安娜兄妹在童话世界开启冒险，遇见各类精怪和女巫，最终找到妈妈的故事。玩法上，游戏是回合制战斗 RPG。美术采用16x16像素风格，声效为仿GBA/FC时期的8bit声效。DEMO已搭建装备/背包/战斗/队伍管理/身份等多个系统的原型，并实际填充了主线剧情和相关事件，可以有完整的游戏体验。
## 我的角色
单人制作人：负责主策划案的撰写。主导世界观、剧情与数值设计，统筹战斗、装备、队伍、背包、存档、商店等系统落地。并通过【制作人把控框架 → 主脑 AI 拆解任务卡 → 助手 AI 执行 → 联合验收】的三方协作流程。职责划分清晰，三方在顶层设计/判断复核/落地执行的三个层面各司其职。使主脑AI对项目的架构记忆清晰，决策讨论出错率低；助手AI则可根据需求随时更替，灵活性强，性价比高。
## 开发细况
DEMO的开发时间只有十天，非常紧凑。因此刚开始方向能否锚定的清晰，案子能不能写的有取舍非常重要。在简单构思世界观在游戏语境下的转换方案之后，我敲定了指令式战斗的大框架，并且在此基础发散填充，完成了最初版的游戏策划案。之后策划案在与AI的讨论之下查缺补漏，趋于完整。但是策划案≠游戏落地，在游戏落地执行的初期，因为缺乏AI开发较大型项目的经验，很快就吃了上下文的亏——即使拥有项目记忆，也架不住同时担当主脑与执行的强度，而且不断积累的上下文会蚕食每一次重置后的空间，每一次不稳定的压缩都有可能造成AI记忆的混乱，有一次让主脑做一个问题的检修，穷尽算力的主脑在检修之后上下文几乎掌握不住重点了。在这种情况下，我决定分化职能，于是初步描摹了三方合作的图景“我管理核心的数据源和策划案，设置主脑AI和执行AI，主脑只掌握架构，向我对齐理解，派发任务卡，任务中包含新内容则给出技术实现建议，bug修复则只给出猜想和检修方向建议，不做无意义的穷举；执行Agent只通过README.md配置能够确立自己工作方法的相关知识库和Agent设定，不绑定复杂的上下文，只负责每一张任务卡中板块明确的任务执行”这个构思和协作方法论有效地解决了问题，让开发过程变得顺畅且清晰。
## 结果与复盘
前期虽有一定曲折的探索，但是在调整，完善了方法论和协作流程之后。在保持效率和性价比的情况下推完了DEMO开发的全流程。这次宝贵的开发经历帮助我厘清了当前AI的职能运用与缺点，探索出了与AI沟通的心得与协作方法论。我认为系统是由许多规则组合而成的集，用于完成某个功能。如果从这个角度思考，那么我完成的不止是游戏DEMO和玩法系统的策划案，而且也在通过不断为不同定位的AI明晰规则之中，让他们成了能明确负责某个功能和模块的”系统“。

- **战斗系统**：速度排行动序、攻/技/道/防/逃五指令、明雷遇敌、多敌人战斗、敌人 8 种 AI 范式（鲁莽 / 逼近者 / 规律技击 / 随机技击 / 蓄力怪 / 间歇跳过 / 远程压制 / 权重随机）。
- **距离机制**：距离影响命中，距离影响AI行动，基于此套核心准则设计拓展指令式战斗的博弈乐趣，让玩家可以通过保持/拉近距离的正确决策博弈创造行动经济，享受决策致胜带来的快感。
- **数值调控**：小量级的数值成长和简单的伤害计算公式返璞归真，让玩家专注机制博弈，而不是简单的数值碰撞；物理伤害 = max(攻击力×0.6 − 防御力×0.4, 攻击力×0.15)；命中率 = clamp(85% + 灵巧差×2% − 距离惩罚, 5%, 100%)。
