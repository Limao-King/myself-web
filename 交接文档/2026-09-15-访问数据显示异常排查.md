# 排查记录 · 2026-09-15 · 「Web Analytics 有 223 次浏览，cmd 却查不到记录」

> 本文是**排查记录**，不是契约。状态权威仍是 `交接文档/CURRENT.md`（本次**没有改它**）。
> 结论一句话：**采集端点从头到尾都正常，是读取脚本把「网络超时」误报成了「没有记录」。**

---

## 1. 现象（用户的两次输入）

- Cloudflare Web Analytics（引用方视图）：总计 **223**；`www.limao.site` 216 / 无（直接）5 / `cn.bing.com` 2。时间轴上 15:00、18:00、20:00 有三个 60–67 的尖峰，本地 13:11（UTC 05:11）那次 tooltip 显示「部分数据」。
- 同一时刻在 cmd 里跑 `node scripts/view-visits.mjs --days 7`：**共 0 条记录（显示 0 条），查询 7 天（7 天无对象）**。

## 2. 证据链

| 证据 | 方法 | 结果 |
|---|---|---|
| 线上 Worker 在岗 | `GET https://play.limao.site/hit` | **405 + `Allow: POST`** —— `/hit` 分支已部署 |
| Origin 白名单生效 | 坏 Origin 的 `POST /hit` | **403** |
| 浏览器式 POST | 带 `Origin: https://www.limao.site` + 常规 Chrome UA | **204** + `Access-Control-Allow-Origin` + `no-store` |
| 线上首页带着上报脚本 | `GET https://www.limao.site/` | 29,583 字节，含 `sendBeacon`、`play.limao.site/hit`、`setTimeout(send, 1000)` |
| 写链路通 | 发一次探测 POST 后再读 | R2 当天对象**立刻出现该行** |
| 读链路通 | `node scripts/view-visits.mjs --days 2` | **09-14：6 条；09-15：3 条** |
| ⭐ 真因 | 读 wrangler 本机日志 `%APPDATA%\xdg.config\.wrangler\logs\` | 13:11 那两轮 14 次 `r2 object get` 里，**5 次是 `TypeError: fetch failed`（连接超时 10.7 秒）**，6 次是正常的 `key not found` 应答 |

`fetch failed` 证明当时的**对象是存在的** —— 请求根本没拿到应答，更不可能得到"不存在"这个结论。

## 3. 根因（两条，叠加）

1. **`scripts/view-visits.mjs`（旧版）把三类结果吞成一类**：`fetchDay` 的 `catch { return null }` 对「网络超时 / 对象不存在 / 权限失败」返回同一个 `null`，上层再把它计入"无对象"并打印那三句"没有记录。可能原因：①②③"。于是 **10.7 秒的连接超时被显示成"没有访问"**。
2. **本机出口到 Cloudflare API 不稳**（大陆网络环境）：同一批命令里"超时 / 正常应答"交替出现；`play.limao.site` 的 `colo` 分别落在 SEA / LHR / SJC（绕行严重），与"重试是常态"一致。

**为什么两台数字本来就不该相等（不是同一种计量）**：

- Web Analytics 223 = **执行了 JS 的客户端**的聚合计数（Cloudflare 自带信标），不含 94% 连 JS 都没跑起来的爬虫（那部分只有 19,532 次服务器侧请求那种口径才看得到）；
- 反过来它也**不代表真人**：三个 60–67 的尖峰、间隔规整，是脚本/无头浏览器/监控的典型形状；
- `/hit` 才是"有没有真人"的尺子（UA / 国家 / ASN / 时间 / 路径 / 来源页 / 当日加盐 IP 哈希）。
